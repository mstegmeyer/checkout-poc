# Upstream issue drafts: `POST /store-api/shipping-cost/cart` (Shopware 6.7)

> **Update 2026-08-18:** filed as a fix PR instead:
> https://github.com/shopware/shopware/pull/19419 (branch
> `fix/shipping-cost-cart-route`, both bugs fixed + unit tests + changelog).
> The drafts below remain as the reference analysis.

Two independent bugs in the new delivery-cost route
(`Shopware\Core\Checkout\Cart\SalesChannel\ShippingCostRoute`, introduced in
[shopware/shopware#15827](https://github.com/shopware/shopware/pull/15827)).
Both reproduced 2026-08-18 against trunk (`6.7.9999999-dev`, commit `1798e9b88f2`)
with plain curl, no plugins involved. File as **two separate issues** — the root
causes are unrelated (one is a clone problem, one is a persister problem).

Related history for issue 1: [shopware/shopware#1189](https://github.com/shopware/shopware/issues/1189)
was the same class of bug in 2019 (cloning a cart whose ErrorCollection contained a
`ShippingAddressBlockedError`).

---

## Issue 1 — 500 "Trying to clone an uncloneable object" when the cart has errors

### Summary

`POST /store-api/shipping-cost/cart` answers **HTTP 500** whenever the cart's
`ErrorCollection` is non-empty, e.g. when it contains a `ShippingMethodBlockedError`:

```json
{"errors":[{"code":"0","title":"Internal Server Error","detail":"Trying to clone an uncloneable object of class Shopware\\Core\\Checkout\\Shipping\\Cart\\Error\\ShippingMethodBlockedError"}]}
```

Since the route exists to show *alternative* shipping costs, "the currently
selected shipping method is blocked" is precisely the state in which a
storefront wants to call it — and precisely the state in which it crashes.

### Root cause

`ShippingCostRoute::resolveCartDeliveries()` does `clone $originalCart`
(`src/Core/Checkout/Cart/SalesChannel/ShippingCostRoute.php:127`). `Cart` uses
`Struct`'s `CloneTrait`, which deep-clones every property — including the
`ErrorCollection`, whose own deep-clone clones each element
(`src/Core/Framework/Struct/CloneTrait.php`). But `Checkout\Cart\Error\Error`
extends `\Exception`, and PHP exceptions are not cloneable (`Exception::__clone`
is `final private`), so `clone` throws
`Error: Trying to clone an uncloneable object of class …` for **any** cart error,
not just `ShippingMethodBlockedError`.

### Reproduction (demo data)

```bash
KEY=<sales-channel-access-key>

# 1. Add a product whose cart blocks a shipping method. With default demo data any
#    cart total outside the Standard price matrix does it ("no shipping costs found").
curl -s -D - -o /dev/null -X POST http://localhost:8000/store-api/checkout/cart/line-item \
  -H "sw-access-key: $KEY" -H "Content-Type: application/json" \
  -d '{"items":[{"type":"product","referencedId":"<expensive-product-id>","quantity":1}]}'
# → response body contains errors["shipping-method-blocked-Standard"],
#   response header sw-context-token: <TOKEN>

# 2. Ask for shipping costs
curl -s -w "\nHTTP %{http_code}\n" -X POST http://localhost:8000/store-api/shipping-cost/cart \
  -H "sw-access-key: $KEY" -H "sw-context-token: <TOKEN>" \
  -H "Content-Type: application/json" -d '{}'
# → HTTP 500, "Trying to clone an uncloneable object of class ...ShippingMethodBlockedError"
```

Any other cart error (promotion notices, address blocked, …) triggers the same
crash; `shipping-method-blocked` is just the easiest to produce with demo data.

### Expected

The route returns costs for the calculable methods; cart errors must not make it
crash. (See #1189 for the 2019 incarnation of the same clone-an-Error problem.)

### Suggested fix

Exclude the errors from the clone — they are irrelevant for the what-if
calculation and are regenerated by the processor anyway:

```php
// ShippingCostRoute::resolveCartDeliveries()
$errors = $originalCart->getErrors();
$originalCart->setErrors(new ErrorCollection());

try {
    $cart = clone $originalCart;
} finally {
    $originalCart->setErrors($errors);
}
```

A more durable fix would be `Cart::__clone()` resetting `$errors` (or
`ErrorCollection` skipping element clones), so the next `clone $cart` call site
doesn't reintroduce the crash.

## Issue 2 — a 200 response deletes the persisted cart (next cart read is empty)

### Summary

When `POST /store-api/shipping-cost/cart` succeeds (HTTP 200), it **deletes the
customer's persisted cart**. The next `POST /store-api/checkout/cart` for the
same context token returns an empty cart (0 line items). Observed directly in
the DB: the row in `cart` for the token exists before the call and is gone after.

### Root cause

Chain of four steps:

1. `ShippingCostRoute::resolveCartDeliveries()` clones the cart — **the clone
   keeps the original token** — and recalculates it via
   `CartRuleLoader::loadByCart()` with a `CartBehavior` containing
   `CheckoutPermissions::SKIP_CART_PERSISTENCE`
   (`ShippingCostRoute.php:133-138`).
2. The recalculation with a different shipping method changes the cart's error
   hash / content, so `CartRuleLoader::load()` decides it must save:
   `$this->cartPersister->save($cart, $context)` (`CartRuleLoader.php:114-120`).
3. In `CartPersister::save()`, `shouldPersist()` returns `false` **because of**
   `SKIP_CART_PERSISTENCE` (`AbstractCartPersister.php:45`).
4. `save()` treats "should not be persisted" as "**delete the stored cart**":
   `$this->delete($cart->getToken(), $context)` (`CartPersister.php:90-95`) —
   and because the clone shares the real cart's token, this deletes the
   customer's actual cart row.

So `SKIP_CART_PERSISTENCE` does not mean "leave storage alone"; via
`CartPersister::save()` it means "delete the stored cart". The route author
clearly intended the former.

Note the deprecated guard right above
(`CartPersister.php:81`): pre-6.8, recalculation carts
(`$cart->getBehavior()?->isRecalculation()`) hit an **early return** — no
delete. `SKIP_CART_PERSISTENCE` is the designated v6.8 replacement for that
flag, but it takes the delete branch instead of returning early. Once
`v6.8.0.0` removes the `isRecalculation()` early return, every consumer of
`SKIP_CART_PERSISTENCE` that recalculates a live-token cart (e.g.
`OrderConverter`-style flows) inherits the same delete-the-real-cart hazard.
(`ProductShippingCostRoute` is unaffected: it builds a fresh cart with a random
token and calls the `Processor` directly, never the persister.)

### Reproduction (demo data)

```bash
KEY=<sales-channel-access-key>

# 1. Add a product; select a shipping method that works so the cart is error-free
#    (avoids issue 1) — with demo data: Express.
curl -s -D - -o /dev/null -X POST http://localhost:8000/store-api/checkout/cart/line-item \
  -H "sw-access-key: $KEY" -H "Content-Type: application/json" \
  -d '{"items":[{"type":"product","referencedId":"<product-id>","quantity":1}]}'
# → header sw-context-token: <TOKEN>

curl -s -o /dev/null -X PATCH http://localhost:8000/store-api/context \
  -H "sw-access-key: $KEY" -H "sw-context-token: <TOKEN>" -H "Content-Type: application/json" \
  -d '{"shippingMethodId":"<express-shipping-method-id>"}'

# 2. Cart is fine: 1 line item
curl -s -X POST http://localhost:8000/store-api/checkout/cart \
  -H "sw-access-key: $KEY" -H "sw-context-token: <TOKEN>" -H "Content-Type: application/json" -d '{}' \
  | jq '.lineItems | length'   # → 1
# DB check: SELECT COUNT(*) FROM cart WHERE token = '<TOKEN>';  → 1

# 3. Ask for shipping costs — succeeds
curl -s -o /dev/null -w "HTTP %{http_code}\n" -X POST http://localhost:8000/store-api/shipping-cost/cart \
  -H "sw-access-key: $KEY" -H "sw-context-token: <TOKEN>" -H "Content-Type: application/json" -d '{}'
# → HTTP 200 with correct per-method costs

# 4. Cart is gone
curl -s -X POST http://localhost:8000/store-api/checkout/cart \
  -H "sw-access-key: $KEY" -H "sw-context-token: <TOKEN>" -H "Content-Type: application/json" -d '{}' \
  | jq '.lineItems | length'   # → 0
# DB check: SELECT COUNT(*) FROM cart WHERE token = '<TOKEN>';  → 0
```

### Expected

A read-only cost preview must never mutate, let alone delete, the persisted cart.

### Suggested fix

Make `SKIP_CART_PERSISTENCE` an actual no-op in `CartPersister::save()` — an
early return mirroring the old `isRecalculation()` guard, before the
delete-branch logic:

```php
// CartPersister::save()
if ($cart->getBehavior()?->hasPermission(CheckoutPermissions::SKIP_CART_PERSISTENCE)) {
    return;
}
```

(The `shouldPersist()` check must keep the permission for the case where the
event forces persistence, or the flag can be dropped from `shouldPersist()`
once `save()` returns early.)

Defense in depth: `ShippingCostRoute::resolveCartDeliveries()` should also give
the cloned cart a throwaway token (`$cart->setToken(Uuid::randomHex())`, as
`ProductShippingCostRoute` effectively does), so a what-if calculation can never
address the customer's stored cart even if persister semantics regress again.
